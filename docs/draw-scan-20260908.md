# Exact draw preparation scans — September 8

This opt-in candidate reduces CPU work while retaining the exact submitted data.
Native, host, ARM and private emulator checks pass. It is **not installed on the
Vita**, and no hardware FPS gain has been established.

## Change

The index path previously copied each chunk into a cached temporary, scanned
its maximum index, then copied it into the uncached GPU ring. The new ARMv7 NEON
path bounds and retains the same loaded values in one pass. It handles odd
source addresses, short tails and index 65,535 without reading outside the
requested span or reading back uncached GPU memory. Sequential and already-owned
quad buffers keep their existing path.

Shader constant synchronization now has an exact vector equality option using
the existing byte comparator. It still checks all 3,072 bytes, copies changed
constants and increments their generation. No float equality, hash, stale
generation or pointer-only cache substitutes for that check. Signed zero, NaN
payloads and the UI's partial constant overrides remain distinguishable.

`XV_DRAW_SCAN_NEON=1` enables both paths. The default is **off** pending hardware
measurement. The per-window `draw-scan` line reports index counts and unchanged
constant checks without adding per-draw clock reads.

`XV_BENCHMARK_DRAW_SCAN=1` selects scalar/vector/scalar for **L + R + Square**.
It holds resolution, visibility scheduling, queue policy, vertex residency,
shaders and graphics settings fixed. Completion, cancellation and loss of the
gameplay view restore the configured scan setting. Without this selector, the
installed/default comparison remains eager/deferred/eager visibility.
The later vertex-copy selector takes precedence if both developer selectors are
set; leave it unset for this test.

## Verification

- Host draw-preparation tests pass: both index paths, shader/state caches,
  exact constant changes at every byte, partial UI writes and generation wrap.
- ASan/UBSan checks pass for index copying and the real constant setter.
- The Vita compiler's Cortex-A9 instructions pass **2,119 index cases** and
  **6,146 constant cases** under Unicorn with exact read/write bounds. Tests
  include unaligned inputs and destinations, every lane carrying the only maximum,
  full pools, unmapped end pages and generation wrap. `sceClibMemcpy` is modeled
  as a byte copy; this does not test firmware timing or SGX543 behavior.
- Frame acquisition/completion and the actual benchmark hook preserve slot
  ownership and change only the selected optimization.
- Native builds pass in an isolated stage based on the installed September 8
  source, without unrelated root experiments or shader changes.

The private Vita3K run covers ordinary solo countdown/launch, camera turns,
firing, movement and flashlight input, grenade self-death/body/respawn, Pause /
Leave Game, campaign loading, the opening cinematic through the Keyes view,
skip into cryo gameplay and further camera turns. It does not establish full
campaign or audible music correctness.

| Blood Gulch | 19.959 FPS | 19.966 FPS | 19.959 FPS |
| Campaign cryo | 19.484 FPS | 19.527 FPS | 19.133 FPS |

Each phase excludes 60 settling frames and measures 120 frames. Camera checks
pass. Blood Gulch reaches the 20 FPS cap; the campaign variation does not
establish a gain. These results validate the switch and exercise rendering;
they do not predict Vita speed.

Eleven sampled ownership checks cover **2,812 draws**, with zero geometry-byte
changes before GPU completion. No logged upload failures, draw-storage drops,
constant rejections, fence errors or ordinary Finish calls occur. Maximum upload
usage is 1,982/8,192 KiB per slot and maximum pending GPU packets is one. The
opening cinematic reaches 1,291 GXM draws in a frame, a separate workload from
the much lower draw counts in the measured hardware Blood Gulch session.

The Vita3K backend console separately reports fragment/vertex varying-link
errors, also present in the earlier baseline. Game-side GXM success checks do
not establish that every emulator pass rendered. This pre-existing shader issue
has a separate [rendering candidate](shader-varyings-20260908.md) and limits
visual/timing conclusions from this run.

The emulator is stopped and its previous executable/configuration restored.

## Expected size of the opportunity

The previous hardware log attributes roughly 2 ms/frame to index preparation
and draw setup, which includes these constant checks and other work. Removing
that entire interval would still leave the 90.88 ms frame far from 50 ms.
In the initial private Blood Gulch view, 5,460 of 9,240 constant checks were
unchanged, so the repeated-read case occurs often enough to test.

ARM instruction counts fall from 20,878 to 3,868 for a 4,096-index example and
from 8,518 to 1,495 for an unchanged constant window. These counts exclude the
firmware copy implementation, cache effects, instruction latency and GPU time.
They justify a hardware comparison; they are **not** a measured speedup factor.

First collect the installed visibility comparison. Then compare this candidate
at unchanged settings if it remains the next useful experiment.
